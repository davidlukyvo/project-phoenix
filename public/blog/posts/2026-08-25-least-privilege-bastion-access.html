Least Privilege in Practice: Designing Bastion Access Without Full Sudo

The hard part of secure remote administration is not creating access. It is creating only the access required to do the job.

A common enterprise requirement is to let an engineer or external specialist operate a limited set of systems without exposing the broader production environment. The fastest solution is often to create an account and grant broad administrative privileges. The safer solution is to design an access path around the tasks that person actually needs to perform.

1. Treat the bastion host as a control point

A bastion host should not simply be another server with SSH enabled. It should act as a deliberate boundary between the user and the protected environment. That means the account model, authentication method, allowed destinations and privileged operations should all be designed before access is granted.

2. Prefer key-based authentication

For administrative access, SSH keys provide a stronger and more manageable model than shared or reusable passwords. They also make it easier to separate individual access, revoke credentials and avoid transmitting secrets between people.

3. Scope privileges to operations, not job titles

“Engineer” is not a permission set. If the real operational need is to inspect container status, view logs and restart a service, then the privilege model should reflect those actions. A carefully designed sudo policy can allow a small set of operational commands without granting an unrestricted shell as root.

4. Separate observation from change

Read-only commands such as listing processes or viewing logs carry different risk from restart, package installation or configuration changes. Grouping them into the same privilege level makes access harder to govern. I prefer to identify which actions are observational, which are operational and which truly require elevated administrative authority.

5. Validate the path end to end

Secure access is not complete when the account is created. The engineer should be able to authenticate through the bastion, reach only the intended systems, execute only the approved operations and receive clear failures for everything else. Testing denied actions is just as important as testing successful ones.

6. Document what was granted and why

Access decisions age quickly. A short record of the business purpose, target systems, authentication method, permitted commands and removal conditions makes future review much easier. This is especially valuable when vendors or temporary project resources are involved.

The principle

I think of least privilege as an engineering exercise in reducing the blast radius of a credential. The goal is not to make administration difficult. It is to make the safe path the normal path.

This article generalizes lessons from controlled infrastructure-access design. Internal addresses, hostnames, account names, topology and organization-specific configuration have been intentionally excluded.
